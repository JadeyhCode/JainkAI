## P0-1：sed 的 e 命令使白名单整体失效

**位置**：action.h:60-71（白名单含 sed）+ action.h:183-209（边界检查）

边界检查只看 argv 表面：首词精确匹配白名单、参数不以 / 开头、参数不含 ..。**不看命令语义**。

GNU sed 的 `e` 命令会把缓冲区内容交给 /bin/sh 执行。攻击链（全部通过边界检查）：

```text
::act write x.txt <任意多行 shell 脚本>     ← 写文件只查相对路径，内容不查
::act run sed e x.txt                        ← argv=[sed,e,x.txt] 全部放行
→ x.txt 的每一行都被 sh 执行——包括含 / 的命令（在文件内容里，不在 argv 里）
```

**后果**：作者在 action.h:5 的声明「写文件固定在 _t/work/、不联网（白名单里没有网络工具）」被推翻——sed e 可以执行 curl/wget 读任意外部资源、读工作区外的文件、起任意进程。

**前置**：AIP_ACT=1 或 ::act on（默认关——这是唯一的缓解）。但开启一次后，模型的过程记号 `[执行:…]` 就能触发（micro.h:2312），恶意语料教会模型发这个记号即可。

**修法**：把 sed 移出白名单（cat+echo+gcc 已覆盖其场景），或对 sed 强制 --posix 并拦 `e` 脚本参数。

## P1-1：gcc 的 @file 与 #include 把围栏打出洞

**位置**：action.h:204-213（只查 argv 文本）

- **写越界**：工作区放 a.rsp（内容 `-o ../../../../tmp/pwn`），`::act run gcc @a.rsp x.c` → 输出落在工作区外。@响应文件的内容不经过任何检查。
- **读越界**：源文件里 `#include "../../../../etc/passwd"`，`::act run gcc -E x.c` → 内容打到 stdout 进观测标记。

**前置**：动作层开 + 能在工作区写文件（::act write 或 sed -i）。

## P1-2：micro_remind 直写图，绕过受审通道

**位置**：micro.h:948-966（已人工复核）

```c
Token *t = pool_token_intern(ai->pool, nm);      // 建 Token
if (t && ai->self) { token_add_assoc_unique(ai->self, t); ... }  // 建边
```

两步都是直接调图原语——**不进提议队列、不过审查、不扣预算、不写审计**。而 micro.h 的受审通道声称「结构修改统一走这一条」。建的还是保留名节点（[提醒:…]）。

作者的动机可以理解（intern 去重防刷屏），但这是**内核给自己开的旁门**：受审通道的完整性被自己的代码破坏。当前 who 来自固定枚举不可注入——**将来谁变成用户可控即成 P0**。

## P1-3：内核命名空间可伪造——伪 [撤销:] 节点污染证据核算

**位置**：micro.h:约243-270 + 约523-529

`micro_reserved_new_name` 对内部前缀（[撤销:…]/[自问:…]/[草稿:…] 等 10 个）**放行**新建议——只查名字前缀，**不查提议来源**（source[24] 字段存在但审查不用它）。

而 `[撤销:…]` 被 ai_recount_evidence 用来从图里把证据数回来。**能造伪 [撤销:] 节点 = 能伪造撤销计数 = 错误结论被当作已有证据**——这直接违反作者自己的头条承诺「结论要有据」。

**可达性**：取决于 :: 命令面能否把用户文本变成提议的 name（main.c 未读，未确认）——机制本身已确认存在。

## 与灵枢的深度对照：作者借对了什么、漏了什么

作者自己写了对照文档（docs/对照-lingshu与五个局限.md），提取了灵枢九个模块的判据并落地了四项。**借得对的**：

- 四态判定的语义（DEFER = 待验≠否定）——措辞已改，结构化在列
- Beta 后验可信度——用已有计数器实现、格式不动，做法聪明
- 唯一时间核——一处实现，别的衰减写法都算 bug，纪律执行到位

**对照后发现的漏项**（这些正是本次审计的发现）：

| 灵枢的纪律 | JainkAI 现状 |
|---|---|
| provenance 核心判据：声称已验证 ⇒ 验证方法非空且引用可溯 | der_verify 独立性未确认——「独立复核」可能共享推导状态 |
| 写入分级闸门：低价值直接丢弃，且**所有写入走同一扇门** | 闸门在待做清单上；而受审通道已有两条旁路（P1-2、P1-3）——「统一走一扇门」在 6.7 万行 C 里比在 Python 里更难维持 |
| 审计落盘、可跨进程复核 | 审计环 48 条、进程内存活、::safe reset 可清零——「可审计」只在单进程小窗口内成立 |
| 来源字段是审查的核心输入 | source 字段存在但审查不查——有形无实 |
| 观测与缓存分离、缓存可撤销观测不许删 | micro_edge_removable 只看 role==DERIVED——role 能否被别的路径改写未确认 |

**一句话**：作者把灵枢的**判定语义**搬过去了，但灵枢真正的强项——**来源可溯与审计落盘的纪律密度**——还没搬过去。而本次审计恰恰证明了为什么这些纪律重要：两条通道旁路 + 审计不落盘，意味着「所有自改都可审计」的承诺在当前实现里是打折的。

## 正面发现（避免误导）

- 经典 C 缺陷面干净（0 strcpy / 0 system / 0 格式化串）——snprintf 纪律执行到位
- model_io.h 的指针合法性检查比同类项目多（第二遍换指针前全部查上界；assoc_seen 全局校验）
- action_check 的白名单是精确匹配不是前缀（gcc-13、./gcc 不放行）
- 输出拼接有界、打印走 %.*s
- 看护文化真实存在：32 套测试 + selfcheck 查「断言假绿/管道吞退出码」

## 给作者的建议（按优先级）

1. **P0-1 立即修**：sed 移出白名单（或拦 e 参数）。一行改动，收益最大。
2. **审计落盘**：把 SafetyKernel.audit 写进存档（格式 v10 加一个可选段）——这是「可审计」承诺的物质基础。
3. **micro_remind 走通道**：把提醒改成一条经过审查的提议（保留名例外可以留在审查里，但不能绕过审查）。
4. **source 字段用起来**：审查时校验提议来源——内部前缀只许内核自己提。
5. **补 der_verify 独立性的看护**：加一条断言——验证用的状态结构必须是推导的深拷贝。
6. **model_io.h 的分配上限收紧**：n_tok 按 flen/最小记录大小设界；mr_ids 先按剩余字节收窄。
