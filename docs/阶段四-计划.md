# 阶段四计划：把图扩到「能独立写代码」为止

> 来自用户的下一句要求：**「增加性能，扩大图的大小，扩大到其可以独立写代码为止」**。
> 这一页先把"独立写代码"变成一个**能判定**的东西，再倒推要做什么。
> 判断口径沿用前三个阶段：**没实测的一律标"没测"**；数字都是本机量的。

---

## 一、什么叫「独立写代码」（判据）

四条**同时**满足才算，缺一条就不算：

| # | 判据 | 怎么验 |
|---|---|---|
| ① | **从中文任务描述出发** | 输入只有一句人话（如"读入 N，输出 1..N 的素数"），不允许附带代码或提示 |
| ② | **自己产出可编译的 C11 源码** | 落成 `.c` 文件，`gcc -std=c11 -Wall` 编过 |
| ③ | **自带测试跑绿** | 产物自己打印 `ok`/`FAIL` 断言行并返回 0（阶段二就定下的约定，见 `code_count_asserts`） |
| ④ | **不许作弊** | 没有 per-task 硬编码（不许 `switch(task_id)`）；**消融**：把图里那部分代码知识删掉，通过率必须掉到 0 |

第 ④ 条是关键。没有它，"扩图"和"写代码"可以完全无关 —— 那是自欺。
所以阶段四的主线是：**知识进图 → 从图里查出来 → 组成程序 → 跑绿**，并且用"删掉知识就写不出来"来证明这条链真的在用。

## 二、现状基线（M0，本轮实测）

```
$ sh tests/codebench.sh
A 修复段：3 / 3     ← 给一份只有机械错误的源文件，自己编→看错→改→再编→跑绿
B 合成段：0 / 6     ← 只给一句中文任务描述：**一个 .c 都没产出来**
```

- **A 段（已具备）**：三类机械修法（补分号 / 补 `#include` / 补声明）+ "编不过就还原源码"。
  本轮修掉了它的一个真 bug：缺分号时原来固定补**上一行**，而 gcc 报的是**下一行**的列
  ⇒ 最常见的错一次都修不成功（§6.698）。
- **B 段（还没实现）**：现在它能"改代码"，不能"写代码" —— 没有任何合成通道。
  **0 / 6 就是阶段四要抬起来的那个数。**

## 四、技术路线（先说清楚会做成什么、不会做成什么）

**会做成的**：一个**受图约束的程序合成器** ——
```
中文描述 → 抽意图（读/写/循环/查找/排序…）→ 在图上查"哪套骨架能覆盖这些意图"
        → 骨架带槽位（类型、数组名、循环边界、终止条件）→ 从图的片段里填槽
        → 写出 .c → 走 ::code test 闭环（编→看错→改→跑）
```
知识就是**骨架 + 片段 + 约束**，都以三元组存（`骨架:sum 含 循环`、`片段:sum 初值 0`…），
所以"删掉知识就写不出来"这件事是被结构保证的。

**不会做的**：
- 不做"通用代码大模型"（本仓没有、也不该有）；
- 不扩到任意语言（只 C11；跨语言要重做整条链）；
- 不承诺"任意任务"：只承诺 `tests/codebench.sh` 里那套任务 + 同族任务；
- 不靠"每个任务写一段 if" 充数（那是第 ④ 条判据明确禁止的）。

## 五、性能这一侧（"增加性能"具体指什么）

阶段三已经把**大图能跑**这件事做完了（10⁷ 边 3.59 s / 1.82 GB）。阶段四要的是**真实图也大**：

| 指标 | 阶段三（合成图） | 阶段四目标（真实代码知识图） |
|---|---|---|
| 图规模 | 2×10⁷ 边（占位词） | **≥10⁶ 边**（有意义的代码知识 + 中文词） |
| 载入 | 3.59 s @10⁷ | **≤2 s @10⁶** |
| 单条查询 | 0 ms | **≤5 ms** |
| 存盘 | 6.70 s @10⁷ | **≤2 s @10⁶** |
| RSS | 1.82 GB @10⁷ | **≤1 GB @10⁶** |

**如果真实图到 10⁶ 边时指标不达标**，那就是阶段四要做的性能活（而不是"阶段三已经做完了"）。

## 六、不做清单（照实写下来，免得后面吹）

1. 不做**多语言**（只 C11）。
2. 不做**多文件工程合成**（现在是单文件为主；`::code build` 支持多文件编译，但合成只到单文件）。
3. 不承诺**图灵完备的任意程序合成**：只覆盖骨架库里有的结构。
4. 不把"能编译"当"能写"：判据是**测试跑绿**。
5. 不用"调 API"糊过去：所有产物必须走 `::code test` 那条受审的 gcc 通道。
