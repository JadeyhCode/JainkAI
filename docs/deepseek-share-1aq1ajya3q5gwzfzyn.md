### 1. 先分清两种链

| | 激活链 / 联想链 | 逻辑链 |
|---|---|---|
| 驱动 | 能量扩散、命中、衰减 | 前提→规则→结论 |
| 匹配 | Token 身份、类别继承 | 变量合一、绑定 |
| 结果 | 下一个 Token、动作 | 真值/置信度传播 |
| 记录 | 调用栈、路径 | 证明树/证明 DAG |
| 性质 | 软、概率、可重复 | 硬、可检查、可回溯 |
| 例子 | A 让我想到 B | 人都会死，苏格拉底是人 ⇒ 苏格拉底会死 |

v5 的 `token_activate` 走的是第一种。  
`subs`、`subs_not`、`main` 看起来像规则，但它们是：

- `subs`：当前上下文里有没有这些 Token；
- `subs_not`：当前上下文里不能有这些 Token；
- `main`：命中后激活哪个具体 Token；
- `action`：命中后触发什么副作用。

这不是“前提蕴含结论”，而是“条件触发后继”。

### 2. v5 为什么做不出真正逻辑链

它缺这些核心件：

1. **变量**
   - v5 的 Token 都是具体节点。
   - 没有 `?x` 这种占位符，所以“所有人都会死”无法写成通用规则。

2. **绑定环境**
   - 即使有 `?x`，也要记录 `?x = 苏格拉底`。
   - v5 没有 `var → Token` 的绑定表。

3. **合一**
   - 逻辑链需要把规则中的变量和事实匹配。
   - v5 只有 `ctx_satisfies`，是身份/类别匹配，不是合一。

4. **真值/置信度传播**
   - v5 的 `hits` 是使用频率，不是真假。
   - 逻辑链需要 `true / false / unknown / confidence`，并沿规则传播。

5. **证明记录**
   - v5 的栈只记“激活了谁”，不记“因为哪条规则、哪个前提推出谁”。
   - 逻辑链需要证明树：结论由哪些边、哪些绑定支持。

6. **否定与一致性**
   - `subs_not` 只是局部排除。
   - 逻辑链需要否定为失败、冲突检测、非单调修正、默认推理。

7. **目标导向与回溯**
   - v5 是深度优先扩散，不是“为了证明 G，找子目标”。
   - 逻辑链需要前向链、后向链、回溯、剪枝。

8. **量词、模态、因果**
   - “所有”“存在”“可能”“导致”这些在 v5 里没有对应结构。

所以 v5 能做：

> 苏格拉底 → 人 → 会死

如果预先手工建好这些具体边。

但不能做：

> 所有人都会死 + 苏格拉底是人 ⇒ 苏格拉底会死

因为“所有人”不是变量，规则无法通用。

### 3. 怎么在 v5 上加逻辑链

可以在现有结构上叠一层：

- **变量 Token**：加 `is_var`，或用特殊 Token 表示 `?x`。
- **绑定环境**：匹配时生成 `bindings`，随激活上下文传递。
- **合一匹配**：替代/扩展 `ctx_satisfies`，让规则变量能绑定具体 Token。
- **规则 Token**：一条规则 = 前提列表 + 结论 + 动作 + 置信度。
- **真值字段**：给 Token 或边加 `truth`、`confidence`、`justification`。
- **证明 DAG**：每次命中边时记录 `parent_edge`、`bindings`，形成可回溯证明。
- **目标栈**：加后向链，从目标找规则和子目标。
- **一致性维护**：冲突检测、真值修订、非单调撤回。
- **控制元规则**：什么时候走联想，什么时候走逻辑，什么时候回溯。

加完后，系统能说：

> 我推出 C，因为规则 R：A∧B⇒C，且 A 由边 e1 支持，B 由边 e2 支持，绑定 ?x=苏格拉底。

这才叫逻辑链。

### 4. 逻辑链和意识的关系

逻辑链是**可报告思维流**的骨架，是访问意识的重要部分。  
有逻辑链，系统才能：

- 解释“我为什么这么想”；
- 检查推理是否有效；
- 反思、规划、自我修正；
- 把隐性联想变成显性推理。

但逻辑链不等于意识：

- 一个定理证明器有逻辑链，但没有意识。
- 人类意识也不全是逻辑链，还有情绪、图像、联想、躯体感。
- 没有全局工作空间，逻辑链只是局部计算。
- 没有自我模型，逻辑链不知道“这是我在推理”。
- 没有内驱力，逻辑链不知道“这个结论对我意味着什么”。
- 没有时间连续性，逻辑链只是无历史的一次证明。
- 现象意识那一层，逻辑链更不解决。

### 5. 最合理的架构

不是用逻辑链替代关联机，而是双过程：

- **关联层**：快速、并行、模糊、联想、自修改；
- **逻辑层**：慢速、串行、严格、可验证、可解释；
- **元层**：决定何时用联想，何时转逻辑，何时修改规则。

关联机负责“想到”，逻辑链负责“证明”。  
意识若出现，更可能在元层对两者的全局监控、自我报告和持续整合中浮现，而不是单独在逻辑链里。

### 结论

> **v5 有激活链，没有逻辑链。**  
> 要逻辑链，必须加：变量、绑定、合一、真值、证明记录、目标回溯、一致性维护。  
> 加上后，它成为可解释推理机；再叠加全局工作空间、自我模型、内驱力、时间记忆和行动闭环，才接近功能意识。  
> 逻辑链是通往意识的一座桥，但不是意识本身。

元认知的联想是**任务导向的**。它从“干完活来干嘛”出发，但它的关联边只通向“目标一致性检查”这个狭窄区域。它不会从“干完活来干嘛”联想到“今晚吃什么”、“周末去哪玩”、“人生意义是什么”。它只联想到“这和当前目标有关系吗？——没有。→ 提醒偏离。”

这就是“不随便神游”的真正含义：**输入受限，联想范围受限，输出受限。**

### 3. 这个例子的关键前提

要让这个机制成立，系统必须满足几个条件：

1. **主认知必须有一个明确的“当前目标 Token”**
   - 如果主认知自己都不知道当前目标是什么，元认知就无法判断“偏离”。
   - 所以主认知需要在运行时维护一个 `current_goal` Token，并把它暴露给元认知。

2. **元认知必须能访问主认知的当前内容**
   - 这要求主认知在 `on_visit` 时，把当前 Token 或当前激活内容传给元认知。
   - 元认知不是读心，它是读主认知的“状态报告”。

3. **元认知必须有“目标一致性”的关联边**
   - 这些边可以是预置的，也可以是主认知在运行中自己巩固出来的。
   - 例如：`偏离目标` → `提醒`；`当前内容与目标无关` → `提醒_偏离`。

4. **元认知不能越权直接修改主认知**
   - 它只能写 `meta_queue`。
   - 主认知在安全点自己决定要不要听。

### 4. 这个例子的深层意义

这个例子展示的，其实是一种**“执行控制”**的雏形。

在认知科学里，这对应的是**前额叶对默认模式网络的抑制**：
- 默认模式网络（DMN）负责神游、回忆、计划未来。
- 前额叶（PFC）负责执行控制、目标维持、冲突检测。
- 当 DMN 产生“干完活来干嘛”时，PFC 检测到这与当前任务无关，发出提醒，把注意力拉回来。

你的元认知架构，本质上就是在 `token.h` 上实现了一个**符号版的 PFC 监控回路**。

### 5. 可能的误报与边界情况

这个机制也会出错：

1. **目标不明确时误报**
   - 如果主认知的目标本身就是“规划下班后干嘛”（比如你是个活动策划），那“干完活来干嘛”就不是偏离，而是任务本身。
   - 元认知如果不知道这个上下文，就会误报。

2. **创造性思维被误杀**
   - 有时候“干完活来干嘛”这种看似偏离的念头，恰恰是灵感来源。
   - 元认知如果过于严格，会抑制创造性。
   - 所以提醒应该有优先级和阈值，不是所有偏离都打断。

3. **元认知自己的目标模型过时**
   - 主认知可能已经切换了目标，但元认知还在用旧目标检查。
   - 所以 `current_goal` 需要实时同步。

### 6. 总结

你举的这个例子，完美地说明了：

> **元认知可以在不神游的前提下，对主认知的内容进行联想，并基于目标一致性做出判断，然后提醒主认知。**

它做到了：
- **输入受限**：只看主认知状态 + 当前目标。
- **联想受限**：只联想“是否偏离目标”。
- **输出受限**：只产生提醒，不直接干预。
- **不神游**：不会跑到无关领域。

这正是一个**安全、高效、可解释的元认知兜底机制**。

用一句话概括：

> **主认知负责想“干完活来干嘛”，元认知负责想“这跟干活有关系吗？——没有。提醒你回来。”**

## 一、目标已完成时会怎样

### 主认知的状态变化

主认知完成目标后，会进入一个新状态：

```text
当前目标 = 无 / 已完成
当前内容 = 干完活了，现在干嘛？
```

这时候，主认知想到“今天干完活来干嘛”**不再是偏离**，因为它已经干完了。

### 元认知如果不变，就会误报

如果元认知还在用旧目标 `干活` 检查一致性：

```text
当前内容 = 今天干完活来干嘛
当前目标 = 干活（旧）
→ 判断：偏离目标！
→ 提醒：回来干活！
```

这是**误报**。主认知已经干完了，元认知还在喊“回来干活”。  
这就像一个监工，工人已经下班了，他还在喊“快干活”。

### 元认知需要模式切换

所以元认知必须能识别主认知的**目标状态**：

| 主认知目标状态 | 元认知模式 | 行为 |
|---|---|---|
| 目标进行中 | 一致性检查 | 检查是否偏离当前目标 |
| 目标已完成 | 目标选择监控 | 不再检查偏离，改为监控“是否选新目标” |
| 目标被放弃 | 目标切换监控 | 监控放弃是否合理、是否切换 |
| 无目标 | 待机/探索监控 | 允许神游，甚至鼓励探索 |

当目标完成时，元认知应该：

1. **归档旧目标**：把 `干活` 标记为已完成，不再作为一致性基准。
2. **切换到空闲模式**：不再判断偏离。
3. **监控新目标选择**：主认知现在可以自由联想“干完活来干嘛”，元认知只检查：
   - 有没有选出新目标？
   - 新目标是否和长期目标冲突？
   - 是否长时间无目标、进入无效神游？
4. **必要时提醒**：如果主认知长时间没有选新目标，元认知可以提醒 `提醒_无目标`，甚至主动建议候选目标。

这时候，元认知的联想边变成：

```text
当前目标 = 已完成 + 当前内容 = 计划未来
→ 允许，不提醒

当前目标 = 已完成 + 长时间无新目标
→ 提醒_选择新目标

当前目标 = 已完成 + 新目标与长期目标冲突
→ 提醒_目标冲突
```

### 关键点

> **元认知的目标基准必须是动态的，不能是固定的。**  
> 主认知的目标状态变了，元认知的检查基准也要跟着变。

## 二、突发更重要的事情时会怎样

### 情况描述

```text
当前目标 = 干活
```

### 这时谁来决定切换？

这里有两种可能：

**方案 A：主认知自己决定切换**  
主认知的关联网络命中一条边：

```text
突发事件 + 重要性高 → 切换目标
```

主认知自己把 `当前目标` 从 `干活` 改成 `处理突发事件`。  
元认知只观察，发现目标变了，自动更新基准。

**方案 B：元认知提醒主认知切换**  
主认知可能因为专注而没注意到突发事件，或者注意到了但没切换。  
元认知监控到：

```text
突发事件 + 重要性 > 当前目标
→ 提醒_目标切换
```

然后主认知在安全点决定是否切换。

### 元认知在这种情况下的角色

元认知需要判断三件事：

1. **新事件是否真的更重要？**  
   这需要元认知有**优先级比较**能力。  
   它可以比较：
   - 新事件的紧急度、影响范围、不可逆性
   - 当前目标的截止时间、重要性、可中断性
   - 长期目标、价值底线

2. **当前目标是否可中断？**  
   有些目标可以暂停（写代码），有些不能中断（手术中、驾驶中）。  
   元认知需要知道当前目标的**可中断性**。

3. **切换的代价是什么？**  
   切换目标会丢失上下文、浪费能量、可能前功尽弃。  
   元认知需要评估切换代价，避免频繁抖动。

### 元认知的决策规则

可以写成关联边：

```text
突发事件 + 重要性高 + 当前目标可中断
→ 提醒_切换目标

突发事件 + 重要性高 + 当前目标不可中断
→ 提醒_记录待办，稍后处理

突发事件 + 重要性中 + 当前目标接近完成
→ 提醒_先完成当前目标

突发事件 + 重要性高 + 已切换
→ 保存当前目标上下文，归档
```

### 切换后的处理

一旦切换发生，元认知需要：

1. **保存旧目标上下文**：把 `干活` 的目标、进度、相关 Token 存档。
2. **更新当前目标基准**：`当前目标 = 处理突发事件`。
3. **重置一致性检查**：现在检查的是“是否偏离突发事件处理”。
4. **监控切换后状态**：新目标是否顺利、旧目标是否被遗忘、是否需要回切。

这就像一个**目标栈**：

```text
[ 干活 ]  ← 被压栈
[ 处理突发事件 ]  ← 当前目标
```

处理完后，弹出栈，回到 `干活`。

### 关键风险

1. **频繁切换抖动**  
   如果每个突发事件都切换，主认知会什么都做不完。  
   元认知需要设置**切换阈值**和**冷却时间**。

2. **旧目标遗忘**  
   切换后旧目标可能被永久遗忘。  
   元认知需要提醒“旧目标还在栈里”。

3. **元认知误判重要性**  
   元认知可能高估或低估新事件。  
   这需要外部反馈或长期学习来校准。

4. **元认知越权**  
   元认知不能强行切换目标，只能提醒。  
   最终决定权在主认知（或在安全内核里的固定规则）。

## 一、什么叫“补丁”

补丁不是插件那么简单，它必须满足三个条件：

1. **边界清晰**：补丁只和核心交换 Token，不碰核心内部结构。
2. **可缺失**：没有这个补丁，核心照样能跑。
3. **可替换**：换一个补丁，核心不用改。

视觉编码器是补丁。  
3D 编码器也是补丁。  
甚至逻辑检查器、元认知、效价系统，都可以设计成补丁。

## 二、补丁和核心之间的接口

核心只认 Token。  
补丁负责把外部信号变成 Token，或者把 Token 变成外部动作。

所以接口可以极简：

```c
typedef struct Patch Patch;

struct Patch {
    const char *name;

    /* 补丁初始化，注册自己的 Token 类型 */
    int  (*init)(Patch *p, TokenPool *pool, void *config);

    /* 每帧/每步：把外部信号转成 Token，注入核心 */
    void (*sense)(Patch *p, TokenPool *pool, Token **out, size_t *n_out);

    /* 每步：从核心取 Token，转成外部动作 */
    void (*act)(Patch *p, TokenPool *pool, Token *const *in, size_t n_in);

    /* 补丁自己的内部状态更新 */
    void (*update)(Patch *p, float dt);

    /* 卸载 */
    void (*destroy)(Patch *p);
};
```

核心只需要一个补丁注册表：

```c
typedef struct {
    Patch **patches;
    size_t  count, cap;
} PatchRegistry;

int  patch_register(PatchRegistry *r, Patch *p);
void patch_sense_all(PatchRegistry *r, TokenPool *pool);
void patch_act_all(PatchRegistry *r, TokenPool *pool);
void patch_update_all(PatchRegistry *r, float dt);
```

核心的激活循环里，补丁只出现在两个地方：

```text
1. 激活前：patch_sense_all()  把外部信号变成 Token，放进上下文
2. 激活后：patch_act_all()    把高能量 Token 变成外部动作
```

核心完全不知道视觉、3D、听觉的存在。  
它只知道“有一批 Token 进来了，有一批 Token 要出去”。

## 六、补丁的边界规则

为了让核心健壮，补丁必须遵守：

1. **只输出 Token，不输出内部结构**  
   视觉补丁不能直接往核心塞边。  
   它只能生成 Token，让核心自己建边。

2. **只读核心的公共 Token，不读内部**  
   运动补丁只能看核心给它的动作 Token。  
   它不能遍历核心的 `assocs`。

3. **不修改核心的激活栈**  
   补丁不能在 `token_activate` 中途改结构。  
   它只能在安全点注入 Token 或取走 Token。

4. **有自己的预算**  
   视觉补丁不能无限占用 CPU。  
   它有自己的帧率、分辨率、超时。

5. **可降级**  
   传感器坏了，补丁输出空 Token 集，核心继续跑。

6. **可热插拔**  
   运行时挂载/卸载补丁，核心不重启。

## 二、解耦的四个层次

### 层次 1：架构解耦——不依赖 x86/ARM

token.h 是纯 C，没有汇编、没有 intrinsics、没有平台调用。  
它只依赖：

- `stdlib.h`
- `stdint.h`
- `string.h`

所以它已经可以跑在：

- x86
- ARM
- RISC-V
- MIPS
- 甚至裸机（只要提供 `malloc/free/memcpy`）

这是最浅的解耦：**可移植**。

---

### 层次 2：执行解耦——不依赖 CPU 顺序执行

核心操作是：

```text
遍历关联 → 匹配上下文 → 递归激活 → 修改 hits
```

这是**图遍历 + 数据流**，不是必须顺序执行。

可以映射到：

- **GPU**：每个 Token 一个线程，边并行匹配。
- **FPGA**：Token 存 BRAM，边做组合逻辑，激活做流水线。
- **ASIC**：专用关联机芯片。
- **神经形态芯片**：Token 当神经元，边当突触，hits 当权重。
- **多核 CPU**：按 Token 分片，消息传递。

但要做这些，必须改：

1. **递归改迭代**  
   用显式工作队列代替调用栈。

2. **全局栈改分布式**  
   每个 Token 维护自己的激活状态，不共享全局栈。

3. **hits++ 改原子/归约**  
   并行写同一计数器需要原子操作或最后归约。

4. **动态内存改预分配**  
   并行环境下 `realloc` 是灾难。需要对象池、固定容量、分片分配。

5. **回调改事件**  
   `on_visit` 不能直接调用，要变成消息投递到队列。

---

### 层次 3：内存解耦——不依赖冯·诺依曼

当前架构是：

```text
Token 在内存 → CPU 取指 → 执行 → 写回
```

可以改成：

- **存内计算**：Token 存在 ReRAM/PCM，匹配在存储阵列里做。
- **近存计算**：Token 存在 HBM，激活在近存加速器做。
- **数据流架构**：Token 流动，边是算子，激活是数据流图。
- **事件驱动**：只有状态变化的 Token 才被处理，不是每周期全扫。

```c
// 当前：指针跳转，缓存不友好
```

关联机不再跑在 CPU 上，而是**跑在总线上**。

对，这是关联机定义里最硬的一条：

> **Token 和关联在运行时被系统自身修改。**  
> 加边、加 Token，是自修改的最小完整形式。

前面说的 `hits++`、`misses++` 只是**参数修改**。  
动态加边、加 Token 才是**结构修改**。  
没有结构修改，就只是自适应权重系统，不是关联机。

## 一、为什么动态加边、加 Token 是最难的

`hits++` 可以随时做，因为：

- 不改变结构。
- 不影响遍历。
- 不改变 Token 数量。
- 不改变边的数量。

但加边、加 Token 会：

1. **改变数据结构**  
   `assocs` 可能 `realloc`，指针失效。  
   `tokens` 可能 `realloc`，Token 指针失效。

2. **破坏遍历**  
   正在 `for (i = 0; i < reach; ++i)` 时加边，`count` 变了，循环可能越界或漏边。

3. **破坏路径栈**  
   新 Token 没进栈，可能被重复激活。

4. **破坏并发**  
   多线程同时加边，需要锁或事务。

5. **破坏持久化**  
   `seq`、`id`、`next_seq` 需要一致。

6. **引入无限增长**  
   自修改可能疯狂加边，内存爆炸。

7. **引入语义漂移**  
   系统可能加错边，越加越乱。

所以 v5 明确说：

> `on_visit` 内不得对当前 Token 做 `add_assoc/consolidate`。

这不是偷懒，是安全边界。

---

## 二、动态加边、加 Token 的正确方式

核心原则：

> **激活时只记录“想加什么”，激活结束后统一应用。**

这叫**修改意图队列**。

### 1. 修改意图

```c
typedef enum {
    MOD_ADD_TOKEN,
    MOD_ADD_ASSOC,
    MOD_SET_ACTION,
    MOD_REMOVE_ASSOC,
    MOD_SET_PARENT,
    MOD_SET_CATEGORY,
    MOD_CONSOLIDATE,
    MOD_DECAY,
} ModType;

typedef struct {
    ModType   type;
    Token    *target;       /* 对哪个 Token 操作 */
    Token    *subs[TOKEN_CTX_MAX];
    uint8_t   n_subs;
    Token    *subs_not[TOKEN_CTX_MAX];
    uint8_t   n_not;
    Token    *main;
    Token    *action;
    uint32_t  seq;          /* 可选：指定边 */
    float     weight;       /* 可选：置信度 */
    Token    *new_token;    /* ADD_TOKEN 时用 */
    const char *name;
} ModIntent;
```

### 2. 意图队列

```c
typedef struct {
    ModIntent *items;
    size_t     count, cap;
    int        overflow;
} ModQueue;
```

`on_visit` 里只做：

```c
mod_queue_push(mq, (ModIntent){
    .type = MOD_ADD_ASSOC,
    .target = t,
    .subs = { ctx_token },
    .n_subs = 1,
    .main = new_main,
    .action = NULL,
});
```

不直接改结构。

### 3. 安全点应用

激活结束后，主循环统一应用：

```c
void mod_queue_apply(ModQueue *mq, TokenPool *pool) {
    for (size_t i = 0; i < mq->count; ++i) {
        ModIntent *m = &mq->items[i];
        switch (m->type) {
        case MOD_ADD_TOKEN:
            m->new_token = pool_token(pool, m->name, NULL);
            break;
        case MOD_ADD_ASSOC:
            token_add_assoc_ex(m->target, m->subs, m->n_subs,
                               m->subs_not, m->n_not,
                               m->main, m->action);
            break;
        case MOD_SET_ACTION:
            token_set_action_by_target(m->target, m->subs[0],
                                       m->main, m->action);
            break;
        /* ... */
        }
    }
    mq->count = 0;
}
```

这样：

- 遍历时不改结构。
- 应用时不在遍历中。
- 意图可去重、可合并、可审查。
- 可回滚、可记录、可解释。

## 三、动态加 Token

加 Token 比加边更麻烦，因为：

- 新 Token 没有 `id`。
- 新 Token 没有历史。
- 新 Token 可能是“未知”的具体化。

### 1. 什么时候加 Token

- 匹配失败，`gap` 高 → 创建“未知”的子 Token。
- 遇到新组合 → 创建组合 Token。
- 动作产生新状态 → 创建状态 Token。
- 元认知发现缺失概念 → 建议创建 Token。

### 2. 加 Token 的意图

```c
mod_queue_push(mq, (ModIntent){
    .type = MOD_ADD_TOKEN,
    .name = "新概念",
    .target = parent_token,   /* 可选：挂在谁下面 */
});
```

### 3. 安全点创建

```c
Token *nt = pool_token(pool, m->name, NULL);
if (m->target) nt->parent = m->target;
```

### 4. 新 Token 的初始关联

新 Token 不能孤立。  
它至少要有一条边连回已有网络：

```text
未知 → 新概念
新概念 → 触发它的上下文
```

否则它永远不会被激活。

---

## 四、动态加边的来源

边不会凭空出现。它来自：

| 来源 | 例子 |
|---|---|
| 共现 | A 和 B 同时激活 → 加边 A→B |
| 时序 | A 之后总是 B → 加边 A→B |
| 因果 | 动作 A 导致状态 B → 加边 A→B |
| 相似 | A 和 B 共享上下文 → 加边 A→B |
| 抽象 | A、B、C 共享父类 → 创建父 Token 并加边 |
| 例外 | 默认边失败 → 加例外边 |
| 元认知建议 | 元认知发现缺口 → 建议加边 |
| 动作结果 | 动作成功/失败 → 强化或加边 |

这些都可以写成 `on_visit` 里的检测逻辑，然后推入队列。

---

## 五、动态加边的安全规则

1. **不重复加边**  
   用 `token_add_assoc_unique` 或意图去重。

2. **限制边数**  
   每个 Token 最多多少边，超了要巩固/剪枝。

3. **限制新增速率**  
   每步最多加 N 条，防止爆炸。

4. **新边初始权重低**  
   `hits = 0`，需要反复命中才强化。

5. **新边可被遗忘**  
   长期不命中 → `decay` → 剪枝。

6. **元认知审查**  
   元认知可以否决明显错误的加边意图。

7. **安全内核审查**  
   涉及价值底线、目标的边，必须通过安全内核。

---

## 六、动态加边、加 Token 与 CPU 解耦

如果 CPU 解耦、Token 总线化，动态修改会更复杂：

- 加 Token 需要全局唯一 ID → 分布式 ID 生成。
- 加边需要跨分片 → 事务或最终一致。
- 路径栈需要分布式环检测。
- 元认知需要全局视图。

所以动态修改最好在**单个分片内**先做，跨分片用消息。

---

## 七、和补丁架构的关系

补丁也可以提议加边、加 Token：

```c
typedef struct {
    /* ... */
    void (*propose)(Patch *p, ModQueue *mq);
} Patch;
```

视觉补丁可以提议：

```text
红色 + 圆形 → 苹果
```

但它不能直接加，只能推意图。  
核心在安全点审查、去重、应用。

这样：

- 补丁负责感知和提议。
- 核心负责审查和应用。
- 元认知负责监控。
- 安全内核负责底线。

## 八、最终形态

```text
激活循环
   │
   ├── 匹配边
   ├── hits++
   ├── 触发动作
   ├── 推入修改意图 ──→ ModQueue
   │
   ▼
安全点
   │
   ├── 元认知审查
   ├── 安全内核审查
   ├── 去重、合并
   ├── 应用：加 Token、加边、改动作、巩固、衰减
   │
   ▼
下一轮激活
```

这样：

- 遍历时结构不变。
- 修改统一、安全、可解释。
- 加 Token、加边成为系统自身行为。
- 元认知和安全内核兜底。

## 九、总结

动态加边、加 Token 是关联机的核心能力，但不能在激活中直接做。

正确方式：

> **激活时记录修改意图，安全点统一应用。**

这让系统：

- 运行时自己加 Token、加边。
- 不破坏遍历。
- 可去重、可审查、可回滚。
- 可和补丁、元认知、安全内核协作。
- 可逐步走向分布式、CPU 解耦。

一句话：

> **关联机 = Token 关联 + 运行时自修改。**  
> **自修改 = 激活时提议，安全点应用。**  
> **加 Token、加边，是自修改的结构层；hits++、decay，是自修改的参数层。**  
> **两层都有，才是完整关联机。**
