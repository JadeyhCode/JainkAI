# 并发（§6.582）：契约、分类、做了什么、边界

用户 2026-10-24：「解决并发难题」。

这份文档回答四个问题：**并发到什么程度**（契约）、**哪些东西是共享的**（分类）、
**为了并发改了什么**（清单 + 为什么）、**还有什么没解决**（照实说的边界）。

---

## 1. 契约（能承诺的事，逐条可测）

1. **一个线程 = 一个智能体**。`Agent`（含它的 `AI`、`TokenPool`、修改账、`parts` 上下文）
   **同一时刻只被一个线程使用**。想并行，就每个线程开自己的 Agent。
2. **建脑/加载可以并发**。每个线程各自 `ai_load_file()` / `agent_new()` 是安全的
   （数据表 `patterns.txt` 的懒加载有锁；帧库钩子、池序号、机制表都是原子的）。
   —— 这条是 §6.582 新做到的：以前"先热身一次"是必须的。
3. **问答可以并发**，答案**逐字节等于串行**（`tools/concprobe.c` ①：4 线程 × 12 句 × 4 个脑，
   与串行逐字节比较；TSan 报 0 竞争）。
4. **共享层可以跨线程**：`::brain fork` 出来的脑共享 `emb`（引用计数 + 写前复制），
   多线程同时读、其中一个重建、最后各线程并发释放 —— 表必须归零、内容不能坏。
5. **CLI 仍然单线程**：`main.c` 的命令解析、`::brain` 表、`::parts` 挂载状态都是主线程独占的。
   这一层不打算并发（REPL 本来就是一个人一条线）。
6. **落盘是"不会坏"而不是"会合并"**：模型/段文件/流水都走"唯一临时名 + 原子替换"（§5），
   多个进程同时写同一路径 ⇒ 最后一个赢、文件永远完整；但没有文件锁，读-改-写不安全。

反过来说：**不承诺**的事在 §4 里逐条列着（配置开关在运行中改、跨进程写同一份段文件、
单脑多线程并行问……）。

## 2. 分类：这个仓里 88 个文件级 `static` 变量分四类

> 分类方法：先用脚本把"文件级 `static` 变量"全列出来（88 个），再看每个变量的
> **写入点落在哪个函数**里（加载函数 / 每次问答 / 命令 / 共享结构），
> 最后一类用 TSan 在 4 线程探针下**实测**出来的竞争清单校对。脚本口径与结果见 §6.582 的审计。

| 类 | 是什么 | 处理 | 例子 |
|---|---|---|---|
| **① 数据表**（一写多读） | 启动/首次问答时从 `patterns.txt` / `relations.txt` 读进来，之后只读 | **保持共享**；只把"读文件+填表"整段关进锁里，**装完才立旗** | `g_lead/g_slot/g_shell?/g_reply_*/g_say_*/g_refuse_*/g_bare_*/g_measure_*/g_pron_*/g_verd_*/g_class_*/g_fill_*/g_tail_*/g_syn_*/g_aff_*/g_shape_l/r/g_alias_*` |
| **② 每次调用的暂存** | 这一次问答的草稿：剥壳前的句子、字符 bigram 备忘、打分临时表、壳缓存、计数器、一次性标志 | **`AIP_TLS`（线程局部）** | `g_pre_rhet`、`g_charq`、`g_qidf*`、`g_shell*`、`g_shape_hit`、`g_reply_hit`、`g_last_src`、`g_obs_revised`、`g_rel_guess_hops/visible`、`epoch_seen`、两个 env 缓存 |
| **③ 共享可变结构** | 多线程都会读写的跨脑东西 | **原子 / 自旋锁** | `g_bufref`（emb 引用计数表）、池序号、`g_pat_loaded`、机制表长度、帧释放钩子、`g_think_selfgoal` 开关 |
| **④ 进程/CLI 级** | 只有主线程碰：命令表、多脑表、`::parts` 挂载、代码区、训练计数器 | **不动**（单线程独占） | `g_brains/g_nbrains/g_curbrain`、`g_act`、`g_code*`、`g_note_state`、`g_patch_*`、`g_corpus_check_bad` |

还有一类**原本是全局、这一轮搬进了 `AI`** 的：`g_lf_a/g_lf_r/g_lf_b`（上一轮学到的主语/关系/宾语，
`$A/$W/$O` 会话变量的来源）。它们既是"脑的状态"，全局放着两个脑在同一线程里也会串味 ⇒
迁到 `ai->lf_a/lf_r/lf_b`。顺带把 `aip_note_fact` 的签名改成收 `AI*`。

## 3. 做了什么（每一处都有原因）

| 改动 | 文件 | 为什么 |
|---|---|---|
| `conc.h`：`AIP_TLS`、`AipLock`（C11 `atomic_flag` 自旋锁）、`AIP_ATOMIC_*`/`AIP_LD`/`AIP_ST`、`aip_split_sp` | 新文件 | 只依赖 C11，**不链 pthread** ⇒ 默认构建命令行一字未改 |
| ② 类变量改 `AIP_TLS` | `ai.h`、`agent.h`、`rel.h`、`token.h` | TSan 实测：13 处 `g_charq`、5 处 `g_lf_b`、4 处 `g_lf_r`、2 处 `g_pre_rhet`、`g_shell_*`、`g_reply_hit`、`g_rel_guess_*`、`g_qidf*` |
| 引用计数表加锁 | `share.h` | TSan 报 `g_bufref`/`g_bufref_n`；**不加锁会双释放**：两个线程都看到"计数=2"，各自以为对方是唯一所有者 |
| 池序号改原子自增 | `token.h` | `::brain fork` 可能在别的线程建脑 |
| `patterns.txt` 懒加载加锁 + **装完才立旗** | `agent.h` | 原来是"进门就立旗"⇒ 并发的第二个线程会把半空的表当加载完（TSan 在 `g_alias_*` 上抓到） |
| `emb_randvec` 的查表初始化改 once | `token.h` | 函数内 `static tab/tab_ready`，两个线程同时首次调用会竞争 |
| `strtok` → `aip_split_sp` | `agent.h`（3 处） | `strtok` 的游标在**全局**：TSan 实测一个线程读到另一个线程的栈（`[shape]` 那条） |
| 机制表 / 帧钩子 / 开关原子化 | `think.h`、`ai.h`、`frame_io.h` | 冷启动并发建脑时 `g_think_mech_n`、`ai_frames_free`、`g_think_selfgoal` 竞争 |
| `lf_*` 迁入 `AI` | `ai.h`、`agent.h` | 既是并发问题（TSan 3 处），也是**多脑串味**的老问题 |
| `tools/concprobe.c` + `tests/conc_tsan.sh` | 新文件 | 并发不能靠"看起来没事"：探针逐字节比答案；TSan 报竞争数必须 0 |

## 4. 证据（本机实测，可复跑）

- `tools/concprobe.c` **9 项** + `--cold` **2 项**全过：
  - ① 并行答案 == 串行答案（逐字节，`strcmp`），4 线程 × 12 句；
  - ② **加速 2.82–2.95x**（串行 102–114 ms → 并行 36–39 ms，20 核机器，4 线程；
    不是"一把大锁串起来的"）；
  - ③ 共享层：3 个兄弟共享 emb → 引用计数 4；两个读者 + 一个重建者并发；
    重建后计数 3、重建者有自己的一份；4 个线程**并发释放**后共享表归零；
  - ⓪ 冷启动：4 个线程各自建脑 + 立刻问（并发触发懒加载），答案彼此相同。
- `tests/conc_tsan.sh`：**0 处数据竞争**（两种模式都跑；约 50 秒）。
- 整包 **53/53**（新增 `conc` / `conc_tsan` 两套）、`probematrix` **28 行 diff 为空**、
  `asan_check`(90 命令) 干净 —— 单线程行为一个字节没变。
- TLS 的内存代价：每线程约 **20 KB**（`g_shell` 9 KB + `g_shape_hit` 8 KB + 其余几 KB），
  相对"每个脑一份图"（≈3 MB）可以忽略。

## 5. 跨进程（§6.583）：同一份文件被多个进程写

进程之间的共享只有**文件**：`model.bin` / `*.parts` / 流水 / `frames.txt`。
读的人只做一件事：打开路径 → 读。写的人现在统一走 `saveio.h`：

```
唯一临时名（<path>.tmp.<pid>.<序号>）→ 写 → fflush + fsync + fclose → rename 原子替换
```

- **唯一临时名**是关键：以前是固定的 `<path>.tmp` ⇒ 两个进程同时存同一路径时写的是**同一个**
  临时文件（互相截断/覆盖），而且先 rename 走的那个人会让另一个的 rename `ENOENT`。
  实测（`tests/concfiles.sh`，4 写进程 × 6 次保存）：**旧实现 24 次里失败 13 次**，新实现 **0 次**。
- 语义是"**最后一个 rename 的人赢**"：没有文件锁、没有版本号、不合并。
  需要"读别人的结果再写"（两个进程一起学同一份会话图）仍然不安全 —— 那是 `flock` 的活，没做。
- 段文件的两个写入口（整池 / 只写 delta）现在共用**一份实现**；delta 的"脏标记清零"改成
  **rename 成功之后**才做（以前写失败也会清，等于丢一次 delta）。
- 边界：临时文件与目标同目录（跨目录 rename 不是原子的）；`SIGKILL` 会留下 `*.tmp.*`（无害，无清理器）；
  `action.h`/`code.h` 写生成代码的那两处仍是直写（不是记忆，风险等级不同）；Windows 上
  `rename` 覆盖已存在文件会失败（项目只在 Linux 验过）。

## 6. 照实说的边界

1. **没有"消灭所有全局"**。①类数据表仍是**进程级共享**，靠"进程生命周期里只写一次"这条
   契约成立。这条契约不是编译器强制的：**运行中再去 `aip_patterns_load` 另读一份文件**
   （目前没有这个命令）会破坏它。
2. **②类的 TLS 不是"每个脑一份"**。同一个线程里用两个脑，除 `lf_*` 已进 `AI` 外，
   其余暂存（如 `g_charq` 备忘）仍是该线程共用 —— 但它们每次查询都会重填，
   所以**结果正确**，只是缓存命中率会互相影响。
3. **配置开关**（`g_obs_revise`、`g_rel_chain`、`g_rel_ignore_derived`、`g_rel_guess_visible` 等）
   仍是普通全局：**开线程之后再改会与工作线程竞争**。契约是"开线程前配置好"。
   想运行中改，得给它们上原子/锁（没做，因为 CLI 单线程，现实里没有这个用法）。
4. **单脑仍然一次一句**：并行来自"多脑"，不是"一个问题拆开算"。一个脑同时只允许一个线程。
5. **跨进程没有锁**（但文件不会坏了）：保存走"唯一临时名 + 原子替换"（§5），
   并发写同一路径是"最后一个赢"；**读-改-写**（两个进程一起学同一份图）仍不安全，
   那要 `flock` + 版本号，没做。
6. **TSan 只在 Linux x86-64 + gcc 11.4 上跑过**。`_Thread_local` 是 C11 的，MSVC 要换
   `__declspec(thread)`；`atomic_flag` 是标准 C11，但 arm/32 位没实测。
7. **自旋锁没有公平性**，临界区都很短；唯一的长临界区是 `patterns.txt` 的首次加载
   （一辈子一次）。
8. 没做**工作窃取/线程池**：线程由调用方（CLI 或探针）自己管，库只提供"可并发"的保证。
